## What "100% coverage" actually measures — read this before trusting the headline number

Ground truth was scoped to the scanner's own declared vocabulary: 5 languages, 9 known technology names, 6
known config filenames, 6 known manifest filenames (all literal lists in `lib/project-intelligence/
detectors/`), plus an **exhaustive** comparison of every real dependency and every real top-level file/
directory. This is not a sample — every one of the 134 checks above is a real, individually-verified fact.

It is **not** a measure of "does Juntia understand everything relevant about these projects." It's the
narrower, honest question this phase was actually asked: does the deterministic layer correctly report what
it claims to check for, with real evidence, without inventing anything. On that question, the real answer
across 4 repos and 134 checks is yes, with zero exceptions found.

## Real gaps found (outside the measured vocabulary, not reflected in the coverage score)

- **`pnpm-workspace.yaml` is not a known manifest.** `restaurant-game` uses pnpm workspaces; the scanner
  correctly detects `pnpm-lock.yaml` but has no signal for the workspace file itself. First found in Phase
  12F, re-confirmed here against the same real repo.
- **`@changesets/cli`-class release tooling isn't a known technology.** `claude-toolkit`'s real, load-
  bearing devDependency (`@changesets/cli`) produces zero technology signal — correct given the current
  known-technology list (framework/build-tool oriented), but a real blind spot for release-tooling-shaped
  projects.
- **`tsconfig.node.json` (and any non-exact config filename variant) isn't recognized**, even though
  `tsconfig.json` is. `app-podcaster` has both; only the exact match is detected. Not a bug — the detector's
  own documented behavior (exact filename matching) — but a real, named scope limit.
- **Build-artifact directories (`dist/`) are reported as structure with no distinction from source
  directories.** `restaurant-game`'s `dist/` shows up identically to `src/` in the Structure output — noise
  a human reading `juntia analyze`'s output has to filter mentally, not a factual error.

## A real methodology bug, found and corrected during ground-truth verification

Building `app-podcaster`'s ground truth, an independent `find`-based file count (2 JavaScript files)
disagreed with the tool's real output (4). Traced directly, not assumed: the verification `find` command's
own exclusion pattern (`-path "*/.*" -prune`, meant to skip dotdirs like `.yarn`/`.husky`) also matched
top-level dotfiles like `.eslintrc.js` and pruned them incorrectly — the real detector only skips
*directories* starting with `.`, never individual dotfiles. Re-verified with a corrected `find` command:
4 real files (`lint-staged.config.js`, `.commitlintrc.js`, `.eslintrc.js`, `src/__tests__/setup.js`),
matching the tool exactly. **The tool was right; the first independent check was wrong.** Recorded here in
full rather than quietly fixed, because a benchmark whose own verification process can silently have bugs
undermines the trust the benchmark exists to build — the correction itself is part of the evidence.

## What this benchmark does not cover

- No Python/Go/Ruby/PHP project — every repo tested is Node.js-ecosystem. `requirements.txt`/
  `pyproject.toml` manifest detection and Python language detection remain completely unvalidated against
  any real project.
- No real backend-shaped project (an API server, a database-backed service) — every repo tested is a
  frontend, game, or CLI tool. `express`/`next` (both in `KNOWN_TECHNOLOGIES`) have never been checked
  against a real project that actually uses them.
- No monorepo, no unusually large repository, no repository with a non-standard layout.
- Traversal-cap behavior (`MAX_ENTRIES_SCANNED = 5000` in `language-detector.js`) was never exercised —
  the largest repo benchmarked (`app-podcaster`, ~47 language-matched files) is far below the cap.

## Detectors this benchmark found reliable

`manifest-detector.js`, `structure-detector.js`, `language-detector.js` (including the corrected app-
podcaster case), and `dependency-detector.js` — zero false positives, zero missed facts, across every real
check performed.

## Detectors/vocabulary this benchmark found insufficient (data-justified, not opinion)

`config-detector.js`'s and `dependency-detector.js`'s **known-name lists** (not their detection logic
itself) are the concrete, evidenced gap — `KNOWN_MANIFESTS` is missing `pnpm-workspace.yaml`,
`KNOWN_TECHNOLOGIES` has no release-tooling category, and exact-filename config matching misses real
variants like `tsconfig.node.json`. None of this was fixed in this phase, per its own explicit "no mejorar
detectores durante la primera medición" restriction — every item above is a candidate for a future,
separately-scoped phase, backed by this benchmark's real data rather than a guess.
