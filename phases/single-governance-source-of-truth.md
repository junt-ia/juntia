# Single Governance Source of Truth & Governance In-Flow

Two objectives, resolved together because both attack the same underlying problem: Juntia having exactly one
coherent governance architecture, and a human decision being a real operational mechanism during the
workflow — not a review performed after the fact, and not something a project can be caught between two
generations of.

## Vision this phase is grounded in

> AI interprets. Juntia governs.

Neither objective adds reasoning to Juntia. Objective 1 removes an ambiguity (two governance sources
coexisting) that could itself become a source of contradictory guidance an agent has to reason about.
Objective 2 makes a state Juntia already computes (whether a decision is currently blocking) impossible to
miss, without Juntia ever pausing, executing, or controlling anything outside itself.

## Objective 1: Single Governance Source of Truth

### Audit, before changing anything

Traced through the real code, not assumed:

- **`.juntia/governance/`** — `rules/`, `workflows/`, `roles/`, `skills/`, `conventions/` — is the only
  governance tree any current code path writes to. `bin/juntia.js`'s `SCAFFOLD_FILES` list, `init()`,
  `runIntegrate()`, `runRoute()`, `runSetup()`: every one of them reads or writes exclusively under
  `.juntia/governance/`. `CLAUDE.md` (`agent-integration.js#buildPointerContent`) and `.juntia/BOOTSTRAP.md`
  (`bootstrap.js#buildBootstrap`) — the two files an external agent actually discovers governance through —
  likewise never referenced a legacy path anywhere in their generated content, confirmed by grep across
  `lib/`, `bin/`, and by the pre-existing tests that already asserted it (`test/agent-consumption-model.test.js`,
  `test/knowledge-layer.test.js`).
- **The legacy, flat scheme** — `.juntia/agent-rules.md`, `.juntia/workflows.md`, `.juntia/roles/*.md` — was
  generated by a JS string builder (`agent-governance.js`) that Phase 15B deleted outright when it moved this
  content into `.juntia/governance/` as static, declarative files. No code in this repository writes to any of
  these three legacy paths anymore; `test/knowledge-layer.test.js`'s own "a project with old-scheme files...
  keeps them untouched after init()" test already documented, and locked in, that `init()` deliberately never
  touches them — safe, but permanent. Nothing before this phase ever moved a project off them.
- **`.juntia/agent-instructions.md` is not part of this legacy scheme, and this phase does not touch it.**
  Named alongside the other three in this phase's own brief, but auditing the real code shows it is something
  structurally different: the AI Handoff file (Phase 13D, `lib/project-intelligence/agent-handoff.js`), still
  actively generated by `analyze --explain` today, for a genuinely different job — interpreting this project's
  own *facts* (is this a Phaser project?), never behavioral rules, workflows, or roles. It has no equivalent
  under `.juntia/governance/`, nothing in `.juntia/governance/` replaces it, and `BOOTSTRAP.md` already
  correctly describes it as "a different job." It likely reads as "legacy" only because it sits at
  `.juntia/` root, the same level the old flat files did — a real, worth-recording finding from this audit,
  not a component this phase migrates or deprecates.

### The migration

`lib/project-intelligence/governance-migration.js` is the real conflict-resolution rule
`docs/CLI.md#why-update-was-scoped-narrowly` (formerly "why update isn't built yet") named as the missing
piece — scoped narrowly to this one, now-evidenced migration, not a general "sync any scaffolded file"
engine, which still has no more justifying evidence than it did before.

**The rule**, applied per candidate file (`.juntia/agent-rules.md` → `.juntia/governance/rules/agent-rules.md`;
each `.juntia/roles/<name>.md` → `.juntia/governance/roles/<name>.md`):

1. If the new-scheme file doesn't exist yet, or exists but is still byte-identical to what `templates/governance/`
   itself contains (i.e. `init()` scaffolded it and nobody has touched it since) — copy the legacy content over,
   verbatim. Nothing human-authored is lost, because nothing human-authored was at the new location yet.
2. If the new-scheme file already differs from the stock template — it has already been customized, by a human
   or an earlier migration someone then edited — report a conflict and touch nothing. Free text is never
   merged; Juntia transports content, it does not interpret or reconcile it.
3. If a second `update` finds the new-scheme file already holding exactly the legacy content (the first run's
   own result) — report it as already-migrated, not a new conflict. A real idempotency case a naive
   "does it match the stock template" check alone would have mis-reported.

**`.juntia/workflows.md` (a single flat file) is never split automatically.** Each new-scheme workflow file
requires real, distinct, structurally-parsed sections (`workflow-knowledge.js` depends on
`## Roles involved`/`## Skills recommended`/etc. existing) that a flat file has no reliable mapping onto
without interpreting its content — exactly what Juntia must not do. It is reported as not portable, left
untouched; the new `.juntia/governance/workflows/*.md` files come from Juntia's own defaults instead (already
scaffolded by `init()`, which `runUpdate` calls first, unconditionally, per the same precedent
`runIntegrate`/`runRoute` already established).

**Never destructive**: no legacy file is ever deleted or edited by this mechanism — verified directly by test.
A human decides, separately, when (or whether) to remove one, once they've confirmed nothing more is worth
copying over by hand.

### `juntia update`: the command, finally built

`docs/CLI.md` had reserved `update` conceptually since Phase 12M/12M.5 but left it unbuilt for a real,
stated reason: no evidence yet justified a conflict-resolution rule. This phase's audit *is* that evidence,
so `update` is now real — `runUpdate` in `bin/juntia.js`, reusing `init()` (scaffold current defaults first),
`migrateGovernance()` (the rule above), and `runIntegrate`/`writeBootstrap` (refresh the runtime pointer and
`BOOTSTRAP.md` afterward — the same regeneration every other command touching `.juntia/` already triggers).
No new command family, no new CLI surface beyond the eighth, already-reserved slot `docs/CLI.md` always
counted.

### CLAUDE.md's contract, made explicit

`buildPointerContent` (`agent-integration.js`) gains two short paragraphs — CLAUDE.md stays a minimal entry
point (verified under 2000 bytes by test), never a second index:

1. **`.juntia/governance/` is the single source of truth**, stated once, by name — never enumerating what's
   inside it (that stays `BOOTSTRAP.md`'s job) — with a one-line pointer to `juntia update` for a project still
   carrying the legacy scheme.
2. **The blocking-decision contract, stated at the real entry point**, not only three hops away
   (`BOOTSTRAP.md` → a skill file): if a decision surfacing during work requires human confirmation, do not
   silently pick a default, do not continue implementing the affected part, create a decision request through
   Juntia's own mechanism, wait for `juntia confirm`, continue only once confirmed.

## Objective 2: Governance In-Flow (Task Status)

### The problem, precisely

Just-In-Time Governance (the previous phase) fixed *when* an agent is taught to escalate a decision — no
longer a single pass "before implementing." It did not add a deterministic signal for *whether work is
currently blocked* that survives a session boundary. The gap this phase closes: an agent escalates
(`pending.json` gets a real, valid decision request) and, in the observed M04/Snake behavior, can simply keep
implementing anyway — nothing forced the affected work to visibly stop, and nothing told a **different**
session (context reset, a new window, a day later) that a real, unanswered question was sitting there.

### The state, and why it needed no new mechanism to compute

```
agent works
  -> detects a decision
  -> checks workflow/rules/decision-triggers: BLOCKING or not (agent's own judgment, catalog-informed)
  -> non-blocking: continues (Juntia never sees this — nothing is ever written to pending.json)
  -> blocking: writes a decision request, runs `juntia confirm` (skip if no answer yet)
       -> task-handoff.md: TASK STATUS: WAITING_HUMAN_CONFIRMATION
       -> affected work stops; unrelated work can continue
       -> human answers via `juntia confirm`
       -> task-handoff.md: TASK STATUS: READY_TO_CONTINUE, confirmed value shown
       -> agent resumes the affected work with the real answer
```

`lib/governance/task-status.js#computeTaskStatus` is the whole mechanism — a pure function, no new persisted
state:

- **`WAITING_HUMAN_CONFIRMATION`** whenever at least one currently pending, valid product/architecture
  decision request exists. Unconditional, and deliberately not a judgment Juntia makes twice: anything
  actually sitting in `pending.json` already passed the agent's own BLOCKING test (a non-blocking situation is
  never escalated at all — decision-triggers.md's `Requires confirmation: no` means "continue," not "escalate
  anyway"), so Juntia never re-weighs pending items against each other.
- **`READY_TO_CONTINUE`** when nothing is currently pending but a decision was confirmed since this task
  started — the exact same "since `generatedAt`" comparison `task-handoff.js`'s "Confirmed decisions" section
  (Decision Continuity) already makes, reused, not recomputed differently, so the two can never disagree.
- **`ACTIVE`** otherwise.

### How a blocking decision gets marked WAITING without a new command

The real design question this phase had to answer: Juntia has no hook into the moment an agent writes
`pending.json` (a raw file write, not a CLI call) — so how does `task-handoff.md` learn about it without a
new command Juntia would have to expose? The answer reuses a property `runConfirm` already had:
**it unconditionally refreshes `task-handoff.md` at the end of every run, regardless of whether anything was
actually confirmed.** An agent that escalates a decision and immediately runs `juntia confirm`, answering
`skip` because it doesn't yet have the human's real answer, triggers exactly this refresh — `task-handoff.md`
is rewritten with the current, real `blockingPending` list, correctly showing `WAITING_HUMAN_CONFIRMATION`.
Running `confirm` again later, with the real answer, clears it the same way. Zero new CLI surface;
`governance-review`/`product-decision-making`/`architecture-decision-record`/`agent-rules.md`/`BOOTSTRAP.md`
all now name this explicitly as the mechanism.

### What `task-handoff.md` shows

A new `## Task Status` section, placed first — right after the request itself, before anything else — so it
is the first thing an agent (or a human skimming the file) sees:

```
## Task Status

WAITING_HUMAN_CONFIRMATION

The agent must not continue affected implementation until the pending decision is confirmed.

Pending decisions:

- "How many points does eating one piece of food award?" (product decision, workflow: feature-development)
  Affected area: scoring
  Reason requiring confirmation: A tunable numeric value with no single objectively correct answer.
```

`taskStatus` is also embedded in the machine-parseable Agent Context JSON block (`agent-context.js`'s own
`buildAgentContext`), so a script — not only prose-reading — can check it in one parse. "Affected area" is the
agent's own existing `context` field (already exactly this purpose since Phase 15F); "reason" is a new,
**optional** field on a decision request (`decision-model.js`, `pending-store.js`), transported and displayed
verbatim, never required, never interpreted — an agent may cite the matched `decision-triggers.md` entry's own
reason, its own equivalent judgment, or omit it.

### No "applied" status — restated, still true

`decisions.json` still only ever holds `status: "active"` or `"conflicted"` (Phase 12K, unchanged). Task
Status is a **separate, orthogonal** concept about the current task's own state, computed fresh every time,
never persisted as a fourth decision status. Whether a confirmed decision was actually applied to code remains
entirely the agent's own responsibility — Juntia cannot verify that without patching source itself, which it
must not do, the same reasoning Decision Continuity already established and this phase does not revisit.

### Reviewed, as instructed: workflows / roles / skills / decision-triggers / governance-levels / task-handoff / confirm

- **decision-triggers.md** already had a declarative `Requires confirmation: yes/no` field per situation
  (Phase 15G) — this phase makes it the codebase's *explicit, named* BLOCKING/non-blocking definition (its own
  intro paragraph now states this directly) rather than leaving the implication to be inferred, and
  `governance-review`/`agent-rules.md` now say so too. No Core code changed here — `decision-triggers.js`'s
  parser was already correct.
- **workflows/roles/skills** — no structural change. The four role files each gain one short paragraph under
  their own pre-existing "Escalates to a human when" section, naming the concrete mechanism (which skill, which
  file) generically — real, additive, not a rewrite of Phase-00-era content otherwise left alone.
- **governance-levels.js** — untouched this phase (already reworded by Just-In-Time Governance).
- **task-handoff.js/confirm** — the two real integration points: `buildTaskHandoff` gains `blockingPending`
  (alongside the pre-existing `decisions`/`generatedAt`) and renders `## Task Status` first;
  `refreshTaskHandoffDecisions` gains the same parameter; `runRoute`/`runConfirm` (`bin/juntia.js`) compute it
  via a new, small, read-only `listBlockingPendingDecisions` (normalizes + validates pending items, filters to
  `product`/`architecture` type — an interpretation-type pending item is a different, lower-stakes mechanism
  that never blocks implementation).

**Nothing here is hardcoded in JavaScript about which decisions matter.** `computeTaskStatus` reads counts and
timestamps; it does not know or care what a decision is about. Every piece of content shown — the question,
the area, the reason, which workflow — is transported verbatim from the Knowledge Layer's own declared
catalog (`decision-triggers.md`) or the agent's own free-text fields on the request it wrote. No Snake value,
no specific decision, no specific project's own rule exists anywhere in `lib/` or `bin/`.

## What this phase deliberately does not do

- **Does not make Juntia an agent.** It never decides a decision is needed, never writes a decision request,
  never picks BLOCKING vs. non-blocking — an agent still notices, judges, and chooses, exactly as
  Just-In-Time Governance already established.
- **Does not literally pause an external runtime.** Juntia cannot stop Claude Code (or any other AI coding
  tool) from continuing to generate. The mechanism is a contract and a deterministic, discoverable state — the
  agent (per its own Knowledge Layer instructions) is the one that chooses to respect
  `WAITING_HUMAN_CONFIRMATION` and stop the affected work.
- **Does not introduce a fourth decision status, an "applied" status, or a new persisted task-state store.**
  Task Status is computed, not stored.
- **Does not add a new CLI command beyond the already-reserved, now-built `update`.** No `confirm --id`, no
  `route --resume`, despite both being real, evaluated, named friction points (see Limitations).
- **Does not delete, rewrite, or auto-merge a legacy governance file.** Every migration write is additive at
  the new location; the legacy file is never touched.
- **Does not touch `.juntia/agent-instructions.md`** — audited and found to be a distinct, active, still-needed
  mechanism, not part of this migration.

## Known limitations after this phase

- **`juntia confirm` still visits every pending item in one run, not just one.** With multiple unrelated
  pending items, a human answering via a single piped line only answers the first — verified to degrade
  safely (an unanswered item stays pending via the exhausted-stdin-is-`skip` behavior, never mis-answered), but
  still real friction. A `juntia confirm <id>` flag would resolve it cleanly; deliberately not added this
  phase (no CLI command beyond what evidence already justified) — same limitation Decision Continuity /
  Just-In-Time Governance already named, still unsolved, still tracked.
- **The migration cannot merge two independently-customized copies of the same file.** If both the legacy and
  the new-scheme `agent-rules.md` have real, different human edits, `update` correctly refuses to guess and
  reports a conflict — a human still has to read both and decide by hand. This is the honest limit of "Juntia
  transports, never interprets," not an oversight.
- **`.juntia/workflows.md` is never auto-split.** A project with real, valuable customization in that single
  flat file has to move it into the new per-workflow files manually; `update` only flags that it exists and
  explains why it can't do this automatically.
- **Task Status is honest, not enforced.** Nothing prevents an agent from reading `WAITING_HUMAN_CONFIRMATION`
  and continuing anyway — the same architectural boundary every phase in this Knowledge Layer already respects
  ("Juntia no controla lo que un agente hace — define el entorno en el que trabaja").
- **No live-agent re-validation yet.** Both objectives are verified by direct, real-CLI-function tests
  reproducing the exact reported gaps — neither has been checked against a live agent session yet. That
  remains the named next step, not part of this phase's own deliverable.

## Answers to this phase's own closing questions

1. **¿Existe ahora una única governance source of truth?** Yes for every code path: `init`/`integrate`/`route`/
   `setup` read and write exclusively under `.juntia/governance/`; `CLAUDE.md`/`BOOTSTRAP.md` never reference a
   legacy path. A project that still has legacy files on disk has a real, evidenced, non-destructive path off
   them (`juntia update`) — but until a human runs it (or manually removes the old files), the legacy files
   still physically exist; this phase makes the NEW tree the only one anything reads, not the only one that
   can exist on disk without action.
2. **¿Cómo se migran proyectos antiguos?** `juntia update` — detects the legacy scheme, copies content forward
   wherever safe (new location missing or still the stock default), reports a conflict wherever the new
   location has already diverged, reports `.juntia/workflows.md` as not automatically portable, then refreshes
   the runtime pointer and `BOOTSTRAP.md`.
3. **¿Puede un proyecto creado con una versión anterior actualizarse sin perder reglas humanas?** Yes, verified
   directly: human-customized legacy content survives migration byte-for-byte; a new-scheme file already
   customized by a human is never overwritten, ever — flagged as a conflict instead.
4. **¿CLAUDE.md apunta únicamente al nuevo modelo?** Yes — states `.juntia/governance/` as the single source
   of truth, points a legacy project at `juntia update`, and never enumerates governance/ subdirectories
   (verified by test that the old, pre-15D per-subdirectory enumeration doesn't survive regeneration).
5. **¿Puede un agente externo descubrir la governance sin instrucciones adicionales?** Yes, via the existing,
   unchanged chain — `CLAUDE.md` → `BOOTSTRAP.md` → `governance/` — now also carrying the blocking-decision
   contract and the Task Status mechanism explicitly, at the entry point and at BOOTSTRAP.md, not only inside
   a skill file three hops away.
6. **¿Puede una decisión aparecer a mitad del trabajo?** Yes — verified both before Just-In-Time Governance's
   own escalation timing and, this phase, for the resulting Task Status: a decision escalated after other,
   unrelated work has already happened still produces `WAITING_HUMAN_CONFIRMATION`, with the real question and
   context shown.
7. **¿El agente puede continuar después de confirmación sin memoria conversacional?** Yes — every test in
   `test/governance-in-flow.test.js` re-reads `task-handoff.md` from disk after the fact, never from
   in-process state carried across calls; a brand-new session discovers `WAITING_HUMAN_CONFIRMATION` (or its
   resolution) purely from the file.
8. **¿Juntia sigue sin convertirse en un agente?** Yes — no module in this phase decides a decision, chooses
   BLOCKING vs. non-blocking, writes to `pending.json` on an agent's behalf, or executes anything. Every new
   function added (`computeTaskStatus`, `migrateGovernance`, `listBlockingPendingDecisions`) reads, computes, or
   transports; none reasons about content.
9. **¿La Knowledge Layer sigue siendo la fuente de verdad?** Yes, more explicitly than before —
   `decision-triggers.md`'s `Requires confirmation` field is now the codebase's named BLOCKING/non-blocking
   definition; no decision content, area, or project-specific rule is hardcoded in `lib/` or `bin/`.
10. **¿Qué parte sigue dependiendo del runtime externo?** The actual moment of noticing a decision (an agent's
    own in-context judgment), and the agent's own choice to actually stop the affected work when Task Status
    reads `WAITING_HUMAN_CONFIRMATION` — Juntia makes both maximally discoverable and unambiguous; it cannot
    compute the first or enforce the second.
11. **¿Qué limitaciones siguen existiendo?** See "Known limitations" above — multi-item `confirm`, unmergeable
    dual customization, `workflows.md`'s non-portability, and the honest (not enforced) nature of Task Status,
    all named plainly rather than left implicit.
12. **¿Qué queda pendiente antes de publicar una nueva beta?** Re-running the Snake experiment (or an
    equivalent live session) against both this phase and Just-In-Time Governance together — neither has been
    validated against a real agent yet, only against direct, real-function, real-CLI tests. No release or
    publication was performed this phase, per its own explicit instruction.

**Verdict: CONTINUE.** Both objectives are closed with real, reproduced-then-verified mechanisms: exactly one
governance tree any current code path uses, a real and non-destructive path off the legacy one, and a
decision's blocking status now a deterministic, file-backed signal reachable from the same entry point an
agent already discovers everything else through. The architecture is ready for the next live dogfooding
session to test whether an agent, given only these files, actually behaves this way in practice.
